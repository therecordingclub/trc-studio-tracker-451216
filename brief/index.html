Build the Studio Tracker

An admin tool inside the TRC app that tracks every mixing and video-post project (time, versions, files, client notes) plus a client portal where members send files, review versions, leave notes, and approve. The prototype is the visual spec; this page is the build spec.

01What it is

Three surfaces, one data model. Everything is organized by project, and every file lives in Dropbox.

Mix Room (admin, audio)

  • Projects: singles, EPs, albums, songs
  • Time log with a live timer and an auto-recalculating total (hours are the gold number everywhere)
  • Mix versions as Dropbox links (WAV/MP3) with an inline player
  • Send a version to the client, get their notes back, check each note off as you action it
  • Files in: what the client sent (stems, mixes, references) and what we recorded here

Video Post (admin, video)

  • Identical flow, video vocabulary: editor, cuts, MP4 over Dropbox, 16:9 player
  • Kinds: music video, session film, documentary, reel
  • Same time log, same send and notes loop, same files panel

Client portal (member app)

  • A member sees only their own projects, both audio and video, with a progress timeline
  • Plays the versions we shared, leaves notes, and can Approve (which signs the project off)
  • Sends us files (stems, mixes, footage, references) and sees the studio recordings we made for them
  • Never sees time logs, internal notes, or unsent versions

Overview (admin landing)

  • Five stat cards, click to filter
  • Needs attention: overdue projects, client notes not yet actioned, clients we have waited on for 3+ days
  • Recent activity across both trackers (time logged, versions shared, notes received, approvals, files in)
Pipeline (one status field, five values)Queued, Working (shown as "Mixing" or "Editing" by medium), In review (sent to client), Revisions (client left notes), Approved. Sending moves a project to In review; a client note moves it to Revisions; Mark done or a client Approve moves it to Approved.

03Decisions, with defaults

Build to the default unless Veronia says otherwise. None of these block starting the schema.

1
One engineer/editor, or several?
Default: several. Every project has one assignee (a user). Time entries record who logged them. Filters and stats can be per person later.
2
How do clients get in: member login, or a private link?
Default: member login. Clients are members with accounts, so the portal lives behind the normal login and emails carry a deep link to the project. If a non-member client ever needs access, add a signed link later; do not build that in v1.
3
What is one project: a song, or an EP with many songs?
Default: one project per deliverable (single, EP, album, song, video). Versions belong to the project and carry an optional track_name so an EP can hold "v2 Rough mix, Song A" and "v1, Song B" and the UI groups them. If EPs get messy, add a Tracks level in v2. Do not add it now.
4
Where in the admin?
Default: a Studio hub holding Mix Room and Video Post, per section 02.
5
Who can run the trackers?
Default: admins and Studio Directors (the requireStudioDirectorOrAdmin gate added in PR #943), plus the project's assignee may log time on their own project. Clients never reach these routes.

06Dropbox

TRC runs everything through Dropbox. v1 stores links and plays them inline; no Dropbox API, no files stored in the app.

Playing a shared link inline v1

  • Store the share link as pasted. To stream it, rewrite the query: ?dl=0 becomes ?raw=1 (works for both /s/ and /scl/fi/ links; keep the rlkey parameter on the new format). Feed that URL to a plain <audio> or <video> element. dl=1 forces a download, so never use it for playback.
  • Always show an "Open in Dropbox" button next to the player with the original link.
  • Do not proxy media through the server. Files are large; the browser streams straight from Dropbox.
  • The waveform in the prototype is decorative. A standard player with a progress bar is fine.

Clients sending files v1

  • Create a Dropbox file request per project (done by staff in Dropbox, takes a minute) and paste its URL into dropbox_file_request_url. The portal's "Send us files" opens it; clients drop files with no Dropbox account.
  • After dropping, the client (or staff) records the file with its kind so it appears in the files panels. Staff can also paste a link to a file already in the project folder.

Studio recordings v1

  • Staff adds a file with source = 'studio' and kind = 'recorded_here'. It shows under "From the studio" in the portal so the member can get what was recorded for them.

Later v2

  • Dropbox API app (OAuth): auto-create the project folder and file request, list new files into studio_files, pull duration for the player.

08Permissions

  • Admin routes and pages: requireStudioDirectorOrAdmin on the server and the matching access="studio-mgmt" route guard on the client, so the client predicate equals the server predicate (no see-the-page-then-403).
  • Assignee allowance: a logged-in user who is the project's assignee may add time entries on that project even if not admin or director. Check it in the time routes only.
  • Client routes: requireAuth plus the ownership check in section 05. Clients never see unsent versions, time, internal notes, or other members' projects.
  • Hide affordances the current user cannot use; do not render a button that will 403.

10Definition of done

  • Adding a time entry updates the project total and the overview total immediately; Stop and log on the timer creates an entry rounded to 0.25h.
  • Pasting a Dropbox share link creates a version whose inline player plays (raw=1 rewrite) and whose Open in Dropbox button opens the original link.
  • Send marks the version sent, moves the project to In review, emails the client, and the version appears in the client portal. Unsent versions never appear there.
  • A client note appears on the version in admin, moves the project to Revisions, can be marked addressed, and the overview count updates.
  • Client Approve moves the project to Approved and marks the version approved; Mark done in admin does the same.
  • A due date in the past on a non-approved project shows red on the row and header and appears in Needs attention.
  • User A cannot read or write user B's project through any client route (test returns 404).
  • Every admin route works on admin.therecording.club after re-vendoring, and the Studio hub shows on the admin home and rail.
  • No horizontal overflow at 390px on any screen; no console errors.
  • Vitest: storage methods, status transitions, ownership guard, and the existing route-guard parity test extended for the new routes.

11Build order

  1. Schema and runtime migration, then storage methods on both the interface and the class.
  2. Admin API and the Mix Room list and project pages for audio. Get the time log and versions loop working end to end.
  3. Parameterize by medium and light up Video Post (vocabulary, player, kinds).
  4. Overview endpoint and page: stats, Needs attention, Recent activity.
  5. Client API and portal pages, with the ownership tests.
  6. Emails.
  7. Hub entry, both shells, re-vendor the admin build, PR into main, deploy manually per COORDINATION.md after telling the team.
Not in v1Dropbox API integration, in-app file storage, waveform rendering, a Tracks level under EPs, billing or invoicing tie-ins, realtime updates, non-member client links.

12Repo rules that bite

  • Routes in server/routes.ts, logic in server/storage.ts; keep IStorage and DatabaseStorage in sync.
  • Runtime migrations in server/index.ts; adding a column to the Drizzle schema without one breaks every query on that table.
  • New pages: lazy import plus a Route in the Switch, in both App.tsx and AdminApp.tsx for admin pages; wrap with the right guard.
  • apiRequest() throws on non-2xx; React Query keys are URL paths; staleTime is Infinity, so invalidate after mutations.
  • Do not touch client/src/components/ui/ (shadcn primitives). Icons are Lucide only. Tabs are pill shaped.
  • Dates: parse YYYY-MM-DD as parts; server-side formatting passes timeZone: 'America/Los_Angeles'.
  • Never commit to main directly, never deploy without permission, deploy through bin/fly-deploy or the Actions workflow.
  • No em dashes in any UI or email copy (owner rule).
